# 面向读者的技术产品文档合同

这份合同用于后续修改本目录中的探索文档和 HTML。它不是通用“去 AI 味”词表，而是防止读者入口、术语身份、证据边界和页面层级再次退化的仓库规则。

## 1. 动笔前先写清三件事

每份主文档都要能回答：

1. **主要读者是谁**：业务/管理、产品、架构研发，还是研究复核者；
2. **读完要做什么决定**：理解产品价值、选择方案、拆实施任务，还是核对证据；
3. **用哪一条任务贯穿**：谁提出什么问题，产品读取什么，怎样处理，交付什么，何时停止。

同一页面可以服务多类读者，但首屏只能有一个主要阅读任务。评分、矩阵、命令目录和实现细节不能先于客户问题。

## 2. 功能描述至少包含七个要素

描述一项核心能力时，依次说明：

| 要素 | 要回答的问题 |
|---|---|
| 角色 | 谁会提出这个任务 |
| 原始问题 | 用户会怎样说，而不是内部功能叫什么 |
| 输入 | 需要哪些数据、权限、口径和上下文 |
| 处理 | 产品负责完成哪些关键步骤 |
| 交付物 | 用户最终拿到表、图、报告、草稿、证据还是审批单 |
| 失败行为 | 缺数据、口径冲突、越权、超预算或工具失败时怎么办 |
| 责任边界 | 哪些结论不能下，哪些动作不能自动做 |

不要求每次都机械地做成七列表格，但不能只列模块名和动词。

## 3. 术语必须标明身份

首次出现时，按下列身份说明术语：

- **行业术语**：如 CDC、RLS、OBO、幂等；保留正式名称，并补一句白话解释。
- **厂商正式名称**：保留官方拼写，不改写成自造简称。
- **本文定义**：如 C0–C7、五个平面、Goal Contract；明确写“本文将……称为……”。
- **建议产品名或工作名**：不得写成现有正式产品。
- **组件占位名或接口候选名**：不得直接暗示已经进入代码或发布合同。

`Harness`、CLI、MCP、状态机和控制面属于实现或调用方式。只有说明它们怎样改善客户任务时，才进入业务主线。

## 4. 证据是不允许被文风改写破坏的部分

任何润色都必须保留：

- 事实、数字、日期、版本、区域和 Edition；
- 外部链接、引文含义、证据标签和来源范围；
- `官方声明`、`实际观察`、`推断`、`建议` 与 `Unknown` 的身份；
- 反证条件、失败状态、安全停止条件和 Gate；
- “未找到公开证据”与“产品没有能力”的区别。

没有账号实测时，精确评分只能作为研究方法，不能占据首屏或被写成产品成绩。HTML 设计原型必须标明合成数据、非现网截图和非交付承诺。

## 5. 主线与附录怎样分层

主阅读顺序固定为：

```text
客户问题 → 产品任务 → 当前事实与 Unknown → 决策建议 → 验证方法
```

以下内容按需放入可展开附录，并保证锚点仍可直接到达：

- 精确评分与计算公式；
- 大型能力矩阵；
- 完整 CLI/MCP/API 目录；
- 执行框架、协议字段和部署细节；
- 逐厂商证据与长表。

折叠是改变默认阅读层级，不是删除内容。技术读者仍应能从导航、目录或证据链接进入。

## 6. HTML 验收

- 页面只保留一个主标题；标题先说客户任务或读者问题。
- 桌面和手机首屏都能看出“为谁解决什么问题”。
- 手机主叙事不依赖横向拖动；必须横向浏览的原型或矩阵要给出提示并置于附录。
- 不用大字号精确分数承担主要说服任务。
- 折叠区内的锚点被访问时要自动展开并定位。
- 原型、事实、推断和建议在视觉上身份不同。

修改后运行：

```bash
npm run render:details
npm run validate:decision-site -- http://127.0.0.1:8765
git diff --check
```

浏览器验证至少覆盖桌面 `1440 × 900` 和手机 `390 × 844`，并检查 HTTP、UTF-8、图片、锚点、站内链接、脚本错误与页面整体横向溢出。

## 7. 交付前的无背景读者检查

给没有看过历史材料的人三分钟，只提供目标页面，然后请其回答：

1. 目标产品为谁解决什么问题？
2. 请复述一条从用户输入到结果的任务。
3. 哪些是已经确认的事实，哪些仍是建议或 Unknown？
4. C0–C7、五个平面和 Goal Contract 是行业标准、厂商名称，还是本文定义？
5. 缺数据、无权限或要求高风险动作时，产品会怎样处理？

如果读者只能复述口号、评分和模块名，整改仍未通过。通用 Humanizer 只能在上述结构与证据检查之后，用于发现机械句式；不得替代这一验收。
