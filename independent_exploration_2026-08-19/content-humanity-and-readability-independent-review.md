# 内容“人味”、术语与可读性独立审查

- 审查日期：2026-08-21
- 独立审查者：Ian
- 审查性质：只读内容质量审查，不复核外部产品事实，不修改被审查材料
- 审查对象：`independent_exploration_2026-08-19/` 下的主要 Markdown、HTML 与相关样式
- 核心问题：当前探索材料是否存在“没有人味、AI 味重”，尤其是功能描述既不是清楚稳定的行业术语，也没有被翻译成普通读者能够理解的语言，同时依赖大量未交代前置信息的问题

## 1. 结论

用户的判断**部分成立，而且在核心产品方案与主视觉报告中属于明显问题**；但“整套材料都没有人味、内容都空泛”不成立。

审查信心：**高，约 90%**。

更准确的诊断不是“文档完全没有使用行业术语”，而是三套语言被放在了同一阅读层：

1. **真实行业术语**：例如 `CDC`、`Schema`、`Pipeline`、`RLS`、`OBO`、`MCP`、血缘、幂等。这些术语多数使用方向正确，但面向非专业读者时缺少首次解释。
2. **本文自定义的分析或产品框架**：例如 `Harness-first`、`C0–C7`、五个平面、`Goal Contract`、`Artifact/Evidence`。它们可能有分析价值，但经常以近似行业标准的语气出现，没有稳定标明“本文定义”“工作名”或“组件占位名”。
3. **AI/咨询演示稿式包装**：例如大口号、名词连续堆叠、英文斜杠串、机械对称标签、数字卡片和精确评分。它们让材料看起来完整、系统、权威，却增加了普通读者的理解成本，并可能制造超出证据能力的确定感。

材料底层并非没有内容。客户任务链、功能表、失败行为和验证 Gate 中存在大量具体、扎实、可以执行的内容。因此，主要问题是**读者入口、术语分层和信息呈现**，不是研究应整体推倒重来。

3. **据此做产品或研发的执行者**：需要知道正式对象、边界、输入输出、依赖、失败行为和验收方法。

## 3. 三类读者的实际阅读结果

### 3.1 业务或管理读者

**理解阻力高。**

读者还没有看到一个完整的“谁遇到什么问题、说了什么、系统做了什么、最后拿到什么”，就先遇到 `Harness-first`、`C0–C7`、OBO、CLI/MCP、控制面、信任链、Artifact 和多套评分。

这类读者容易出现三种误读：

- 把本文自定义分类当成行业已经形成的标准；
- 把设计评分当成实测结果；
- 记住口号和数字，却没有建立产品如何工作、为什么有价值的具体画面。

### 3.2 数据平台业内人士

**多数内容可以理解，但阅读仍然费力。**

专业术语本身大多不是错误，问题是以下几类名称没有稳定区分：

- 行业公认概念；
- 厂商正式产品名；
- 本文建议的新产品名；
- 本文分析框架；
- 未来组件占位名；
- 代码或接口候选名。

业内读者需要反复根据上下文猜测“这个词是在描述市场、当前产品、目标架构，还是作者为了组织材料而创建的标签”。

### 3.3 产品和研发执行者

**存在较多可执行内容，但对象身份不够稳定。**

执行者可以从功能表、命令目录、状态、Gate 和安全边界中提取任务。然而，中英混排模块名、多个能力层级的反复映射，以及大量评分，会增加以下风险：

- 把示意名直接固化为正式产品或代码对象；
- 不清楚哪些名称已经被接受，哪些仍是候选；
- 围绕分数优化，而不是围绕用户任务和可验证结果优化；
- 在产品叙事、架构合同和实施清单之间频繁跳转。

## 4. 代表性证据

### 4.1 README 没有先承担“让新读者进入主题”的责任

位置：`README.md:36-42`

原文集中出现：

> Conversation-first / Capability-first / Harness-first、C0–C7、十种结构化回答、88 项 `di` CLI/MCP 原子能力、Goal Contract、Agent 入口治理、十维评分。

问题：README 本应告诉首次读者“这些材料分别回答什么问题、应该从哪里开始”，但该段落先复述内部结构和规模。读者必须先理解项目自己的语言，才能选择阅读路径。

归类：专业术语未解释、项目自造术语、AI 式名词堆叠。

严重度：**高**。

### 4.2 `Harness-first` 在标题和开篇先于定义出现

位置：`huawei-catch-up-product-plan.md:1-8`

原文短摘：

> 华为云 Data Intelligence：能力目标驱动的 Harness-first 领先产品落地方案

> Harness、Goal Contract、CLI/MCP、权限和证据是执行内核

问题：`Harness-first` 不是普通客户能够理解的功能类别，也不是文中明确引用的行业标准。开篇只说明它是执行内核，却没有先用一个具体例子说明：它究竟改变了用户体验、产品交付或研发方式中的什么。

归类：项目自造术语以行业标准口吻出现。

严重度：**高**。

### 4.3 C0–C7 功能表是正面反例，但仍缺两层解释

位置：`huawei-catch-up-product-plan.md:82-93`

该表已经包含：

- 正式功能名；
- 用户会怎么说；
- 产品必须完成什么；
- 主要交付物；
- 优先级。

这是整套材料中较清楚的一部分，证明材料并非普遍空泛。读者能从“最近 30 天华东各地区退款率是多少”“订单库昨晚为什么变慢”等问题建立具体画面。

仍缺少：

1. **目标角色与原始问题**：业务负责人、数据工程师、数据治理人员或 DBA 为什么会使用它；
2. **与相邻能力的区别**：例如智能问数与智能分析、数据知识构建与智能治理之间如何分界。

归类：部分达标，可复用为整改骨架。

严重度：**中**。

### 4.4 设计评分被呈现成了测量结果

位置：

- `huawei-catch-up-product-plan.md:95-110`
- `agent-entry-governance-visual-report.html:510-522`

原文和页面使用：

### 4.5 一行同时混入行业概念、自造模块和组件占位名

位置：`huawei-catch-up-product-plan.md:204-215`

原文短摘：

严重度：**高**。

### 4.6 “五个平面”有内容，但没有标明是本文分析框架

原文标题：

后续表格确实解释了体验、上下文、策略、执行和保证五个平面解决什么问题，因此这不是空口号。问题是标题采用了普遍规律式语气，没有明确标注“本文为比较产品而定义的五层分析框架”。

归类：自造分类、口号化。

严重度：**中高**。

### 4.7 客户任务链是整套研究最自然的部分

位置：`independent-findings.md:173-181`

该表按以下顺序表达：

- 谁付费、为什么；
- 一条完整链路；
- 必要失败行为；
- 产品责任判断。

例如，数据库性能与业务影响联合分析明确写出 DBA/SRE/应用 Owner 的目标、实例遥测到验证的全过程，以及“无实时证据不下根因”“高危动作硬拦截”等失败边界。

这类写法同时满足业务读者、专业读者和执行者，是后续改写时最值得复用的叙事模板。

归类：清楚、具体、自然。

### 4.8 验证 Gate 是执行文档的正面反例

位置：`unknowns-and-validation.md:50-135`

每个 Gate 包含：

- 要回答的问题；
- 测试前提；
- 操作或场景；
- 通过证据；
- 停止条件或安全否决。

它不依赖口号证明价值，而是通过任务、证据和失败结果建立可信度。该文档适合执行者，但不宜未经翻译直接充当业务读者入口。

归类：清楚、可执行。

## 5. 术语问题必须分成三类处理

### 5.1 项目自造术语或命名身份不稳定

典型对象：

- `Harness-first`
- 五个平面
- `C0–C7`
- `Goal Contract`
- `Artifact/Evidence`
- `Path Advisor`
- 一批英文模块组合名

这些词不一定“不专业”，但必须标注身份：

- `本文定义`
- `工作名`
- `建议产品名`
- `组件占位名`
- `接口候选名`
- `非行业标准分类`

其中 C0–C7 已经有较完整定义，问题相对较轻；`Harness-first` 和模块英文串最容易制造误解。

### 5.2 专业术语正确，但缺少面向目标读者的解释

典型对象：

- CDC
- Schema
- Pipeline
- Watermark
- OBO
- RLS/RBAC/ABAC
- Verified Query
- 幂等
- 血缘
- Trace

不建议为了“大众化”把它们全部替换成不准确的普通词。应在首次出现时补一条最小解释：

1. 它是什么；
2. 谁会使用或受到影响；
3. 解决什么问题；
4. 一个具体例子；
5. 必要时说明与相邻概念的区别。

### 5.3 纯表达与 AI 文风问题

典型表现：

- “信任链才是产品”“未来产品不是一张聊天页”等口号先于具体事实；
- WHO/WHAT/HOW/ACT/PROVE 等机械对称标签；
- 多个名词、英文和斜杠连续堆叠；
- 精确到整数、小数或百分比，但没有同等级测量依据；
- 同一结论在路线、能力、模块、原子域和卡片中多次重述；
- 每一节都具有完整、对称、无缺口的咨询模板形态，却缺少真实角色的犹豫、成本、失败和取舍过程。

这类问题不能通过“替换几个高频 AI 词”解决。真正的修复需要重建叙事顺序和读者入口。

## 6. 各 Markdown 的单独判断

### 6.1 `independent-findings.md`

这是主要 Markdown 中最接近真人研究者写法的一份。

优点：

- 事实、推断、建议和 Unknown 边界清楚；
- 客户任务链有真实角色、因果和失败行为；
- 能说明产品组合与单一产品的差别；
- 有条件地表达结论，而不是只给绝对判断。

问题：

- 决策摘要首屏仍有较多厂商名、缩写和产品对象；
- 某些长句一次承载过多边界和限定；
- 可增加一条贯穿全文的业务故事，减少读者在多个产品组合之间切换。

### 6.2 `unknowns-and-validation.md`

对执行者很有效，适合作为验证协议或附录。

优点：

- 问题、测试、证据、停止条件明确；
- 没有用营销材料填补 Unknown；
- 对权限、账号、数据和外部写入保持了安全边界。

问题：

- 不是业务读者的自然入口；
- 缩写和安全概念仍需要词汇表；
- 若放在主叙事前部，会让读者先进入审计模式，而不是先理解产品价值。

### 6.3 `huawei-catch-up-product-plan.md`

这是问题最集中的文件。

根因不是没有内容，而是以下四层被放进了一份连续正文：

1. 产品为什么存在；
2. 客户能够做什么；
3. 内部架构和接口合同；
4. 实施拆解、命令目录和发布 Gate。

当前结构虽然使用章节分隔，但读者仍在同一阅读过程中频繁切换角色。业务读者会过早遇到技术内核；执行者又需要从产品口号和视觉叙事中寻找正式合同。

静态结构指标也反映了这种混合：

- 1647 行；
- 121 个标题；
- 551 行 Markdown 表格；
- 332 处反引号术语或代码片段。

这些数字本身不是质量评分，但说明它已经同时承担产品叙事、架构、规格和接口目录四种文档职责。

### 6.4 `agent-entry-governance-deep-dive.md`

内容有依据，技术判断也有较清楚的边界，但抽象框架、英文术语和评分显著增加了认知负担。

主要问题：

- 本文分析框架与行业术语没有稳定标识；
- 排名和精确分数容易压过不确定性说明；
- 同一内容又以入口、平面、维度、差距、路线多次映射；
- 适合专业专题报告，不适合作为普通读者的第一份材料。

大口号、数字卡片、多列矩阵和大量独立卡片让材料具有强烈的 AI/咨询演示稿外观。页面很“完整”，但读者不容易判断首屏上哪一句是事实、哪一句是推断、哪一个数字真正值得决策。

### 7.3 能力矩阵更适合作为专业附录

这使其适合桌面端的专家核对，不适合普通读者连续阅读，更不适合承担主叙事。

### 7.4 产品原型内容具体，但固定画布掩盖了优点

页面使用固定 `1288 × 763` 产品画布；内部大量文字为 `5.5–11px`。手机媒体规则仍将画布最小宽度设为 `1120px`，依赖横向滚动查看。

原型本身反而较有人味：有用户输入、检查过程、输出、拒绝条件和审批。当前问题是这些优点在桌面上也偏小，在手机上只能局部看到。

## 8. 哪些内容应保留

本次整改不应把材料压缩成另一份泛化营销文案。以下内容具有实际价值，应保留：

- 事实、推断、建议、Unknown 的证据标签；
- 账号级验证边界；
- C0–C7 表中的用户原话、动作和交付物；
- 五条客户任务链；
- 权限失败、数据过期、歧义、超时和高危动作等失败行为；
- Gate、通过证据、停止条件和安全否决；
- 专业矩阵、接口目录和命令目录，但将其降级为专家附录。

## 9. 最小整改优先级

### P0：先重建读者入口

新增一页真正面向业务读者的入口，只使用一个具体角色和一条完整任务：

1. 谁遇到什么问题；
2. 今天怎么解决、哪里费时或容易出错；
3. 用户对产品说了什么；
4. 产品依次做了什么；
5. 用户得到什么可继续使用的结果；
6. 哪些情况下产品会拒绝、暂停或要求人工确认；
7. 这件事为什么值得购买或投资。

在这条故事建立后，再引出能力、产品边界和架构。

### P0：建立术语身份与首次解释规则

为每个术语标明以下身份之一：

- 行业术语；
- 厂商正式名称；
- 本文定义；
- 建议产品名；
- 组件占位名；
- 接口候选名。

标准术语首次出现时使用一句白话解释。本文自定义术语必须明确写“本文将……称为……”，避免伪装成行业共识。

### P0：按读者拆层

建议形成四层：

1. **业务入口页**：一个故事、一项决策、必要边界；
2. **产品能力字典**：角色、问题、输入、动作、输出、失败、相邻能力区别；
3. **研究与比较报告**：事实、证据、Unknown、竞品差异；
4. **技术与验证附录**：架构、接口、原子命令、评分方法、Gate。

### P1：沿用现有功能表，不整体重写

在 C0–C7 表中增加两列：

- 目标角色与原始问题；
- 与相邻能力的区别。

现有“用户会怎么说、系统做什么、交付物”可以保留。

### P1：降低精确分数的视觉权重

内部基线和真实验证完成前：

- 首页使用档位、范围或排序依据；
- 精确分数保留在方法附录；
- 每个分数同时展示证据类型、未验证项和敏感假设；
- 不让单个百分比或小数承担主要说服任务。

### P1：调整 HTML 叙事与响应式阅读

- 主页面减少卡片和矩阵，增加连续故事；
- `67 × 11` 能力矩阵保留为专家附录；
- 产品原型提供响应式重排、放大或全屏模式；
- 正文可读字号不低于约 14px；
- 手机端不依赖横向拖动画布才能理解核心任务；
- 每屏只承担一个判断，并清楚区分事实、推断和建议。

## 10. 后续改写的验收标准

整改完成不能只用“AI 检测分下降”或“句式更口语”验收。建议至少检查：

1. 一名不了解背景的业务读者能否在 3 分钟内回答：产品为谁解决什么问题；
2. 读者能否复述一个从输入到结果的完整任务；
3. 读者能否区分行业术语、厂商名称和本文自定义框架；
4. 每项核心能力是否同时说明角色、问题、动作、输出、失败和边界；
5. 首页是否仍存在未经同等级验证支撑的精确数字；
6. 专业读者能否从业务入口顺利下钻到证据和接口，而无需在多份材料中猜阅读顺序；
7. 手机端是否无需横向滚动即可理解主叙事；
8. 事实、推断、建议和 Unknown 是否在改写后仍被保留。

## 11. 审查边界

- 本次是静态内容与本地渲染审查，不是外部产品事实复核。
- 没有验证屏幕阅读器、键盘操作、不同浏览器或长时间阅读疲劳。
- 没有组织真实业务读者测试，因此“约 90%”是审查者对问题判断的主观信心，不是统计置信区间。
- 没有在本次审查中改写原材料；本文件只持久化审查结论。
- 后续若引入 humanizer 类工具或 Skill，必须单独验证其是否保留术语准确性、事实边界、证据链接和 Unknown，不能仅根据项目热度或输出更口语就判定有效。
